# ddd-base-coding
## 概要
DDD設計のベースとなるコーディングです。

あくまで自身が理想とするDDD設計指針を残すためのリポジトリです。

作成するダミーテーマは適当なゲームっぽいもの（好きなので音ゲーとか？）のバックエンドでも作ろうと思います。

## アーキテクチャ
ドメインを中心に置くDDDを採用する。

また、クリーンアーキテクチャも採用し下記の順番に依存させ、依存関係の逆転をさせない作りにする。

1. [インフラストラクチャ層](#infrastructureインフラストラクチャ層)
2. [プレゼンテーション層](#presentationプレゼンテーション層)
3. [アプリケーション層](#applicationアプリケーション層)
4. [ドメイン層](#domainドメイン層)

### infrastructure（インフラストラクチャ層）
外部システム等の連携を担うレイヤー。

外部システムとは主にはデータベースとやり取りが大半を占める。

名前が長いので以下、インフラ層と称する。

#### 外部システムの都合を閉じ込める
必ず外部システムの都合はこのレイヤー内に収めるようにし、他レイヤーに情報が漏れないようにする。

なぜかというと、下記理由がある。

- 外部システムの入れ替え（DBをMySQLからPostgreSQLに移行等）が、インフラ層の修正のみで対応できる
- 外部システムの仕様が変わってしまった場合、インフラ層の修正のみで対応できる
  - 入力値の桁数や型の変更や、追加削除
  - 出力値の桁数や型の変更や、追加削除
  - エラーパターンの追加
- 外部システムの障害や故障の分析がスムーズで、いち早く外部システムが起因する問題だと特定できる

そのためには、下記のように実装する。

- インフラ層を呼び出す際は必ずインターフェース経由で実行する
- 外部システムのエラーはインフラ層でラップする
- 外部システムのデータの型を直接他レイヤーに返却しない
  - ドメインオブジェクト（ドメイン層）かDTO（アプリケーション層）に変換したうえで返却する
  - もし変換処理が膨大になってきた場合、ファクトリパターンの導入も視野に入れる
- クリーンアーキテクチャの制約上、どのレイヤーにもインフラ層の都合を流出してはいけない

### presentation（プレゼンテーション層）
入出力を担うレイヤー。

RestAPIでいうと、リクエストとレスポンスの管理を行う。

#### リクエストの管理
リクエストパラメーター・リクエストボディ・パスパラメーターなど、フロントエンドなどのAPI実行元から渡される値を取得し、受け取った値は属性チェックを行い、不正値ははじく。

また、認証済みのユーザーIDの取得等も行う。

#### レスポンスの返却
API仕様に基づき、適切なHTTPステータスやJSONでレスポンスを返却する。

| メソッド | HTTPステータス           | 目的            | 安全性 <br /> ※リソースを <br /> 変化させないか | べき等性 <br /> 複数回行っても <br /> 結果が同じか |
|----------|--------------------------|:----------------|:-----------------------------------------------:|:--------------------------------------------------:|
| GET      | 200 OK                   | 取得            |                        ●                        |                         ●                          |
| POST     | 201 Created              | 作成            |                        x                        |                         x                          |
| PUT      | 200 OK <br/> 201 Created | 更新 <br/> 作成 |                        x                        |                         ●                          |
| DELETE   | 204 No Content           | 削除            |                        x                        |                         ●                          |

#### 入出力の都合を閉じ込める
入出力の都合はこのレイヤー内に納めるようにし、他レイヤーに情報が漏れないようにする。

なぜかというと、下記理由がある。

- フロントエンドなどのAPI実行元の入力や出力の仕様変更が、プレゼンテーション層の修正のみで対応できる
  - ゆくゆくは他のレイヤーも修正することになると思うが、初動はプレゼンテーション層の変換のみでスピーディーに対応できる
- クリーンアーキテクチャの制約上、アプリケーション層やドメイン層にはプレゼンテーション層の都合を流出してはいけない

そのためには、下記のように実装する。

- 入力
  - リクエスト（プレゼンテーション層）をドメインオブジェクト（ドメイン層）に変換
  - ドメインオブジェクトをユースケース（アプリケーション層）に引き渡す
- 出力
  - DTO（アプリケーション層）をレスポンス（プレゼンテーション層）に変換
  - DTOをプレゼンテーション層まで届けて、レスポンスに変換したうえでjsonとしてAPIのレスポンスを返却
- 判断（ifやswitch等）を基本的には書かない
  - プレゼンテーション層の責務としては入出力を担うが、判断は別のレイヤーの責務なので入出力の管理に全うする
  - if等を書いてはいけないわけではなく、入出力のチェックに必要であれば書いても問題はなく、入力値によって呼び出すメソッドを切り替えたりはしないという意味
  - プレゼンテーション層での判断が必要ということは、つまり1APIに対する責務が多いということにつながる

### application（アプリケーション層）
システムを動かすうえで必要な設定や、利用者が目的を達成するためのシナリオ（ユースケース）を表現するレイヤー。

#### 設定
アクセス制御などのセキュリティ設定や、データベースの設定など、アプリケーションの設定を行う。

ただし、application.yamlなどに設定するような別レイヤーから参照が必要になる設定は行わず、あくまでアプリケーション層で完結できる設定を行う。

※アノテーションによるDIを駆使して設定

#### ユースケース
達成したい目的や仕事の単位にクラスを分割し、目的を達成するための「誰が・どんな順序で・何をするか」という段取りを表現する。

できる限りガード節で前提条件を判定し、できない場合でも早期リターンを意識する。

ドメインサービスかリポジトリを呼び出し、必要に応じてDTOに整形して返却する。

ユースケース単位でトランザクションを切ることが多い。

#### DTO
プレゼンテーション層へ値を返却する際に使用する形を定義する。

### domain（ドメイン層）
システムの仕様やルール、専門知識などの業務的な処理を担うレイヤー。

どのレイヤーとも依存せず、他のレイヤーの都合に振り回されずに独立した世界を構築する。

#### 値オブジェクト
コンストラクタで属性チェックを行い、値を変更するメソッドを持たない絶対不変の値を保持するクラス。

#### ドメインサービス
業務ロジックを表現するが、
値オブジェクトやリポジトリで解決できない処理のみを書く。

ただし、ドメインサービスから別のドメインサービスを呼ばずに、必ずアプリケーション層のユースケースを経由してやり取りを行う。

#### リポジトリ
インフラ層とやり取りを行うためのインターフェースを定義する。

ドメイン層ではインフラ層を知らないため、インターフェースで行いたい内容だけを定義し、実際にどう実現するかはインフラ層に実装する。

## 設計原則
下記原則を意識して実装する。
- SOLID原則
  - 1クラスの責務は1つに絞る
  - 機能の拡張がしやすく、変更時の影響が少なくなる
  - 子クラスは親クラスの仕様を壊さない
  - 膨大なインターフェースになりすぎないよう、役目などで小さなインターフェースに分割する
  - 具体（クラス）ではなく、抽象（インターフェース）に依存する
- DRY原則
  - 同じ処理を書かないようにするのではなく、同じ意味の処理を書かないようにする
- Tell, Don't Ask(求めるな 命じよ)
  - オブジェクトから情報を求めて処理を行うより、オブジェクトに任せて結果をもらうように実装する
- KISS原則
  - シンプルに保つ
- YAGNI原則
  - 将来必要になりそうだが今は不要な処理を実装しない
